1. Contexte et objectifs

La structure met à disposition plusieurs applications Web internes (gestion de présence, gestion de salaire, gestion scolaire, etc.), chacune gérée historiquement par son propre mécanisme de connexion et d'utilisateurs. Ce cloisonnement impose une multiplicité de comptes, de mots de passe et de table d'utilisateurs à maintenir.

Le projet IAM-Local (IAM ACSI) vise à centraliser :

  • l'Identité — un référentiel unique d'utilisateurs, avec organisation hiérarchique et statut de compte ;
  • la Politique de sécurité — politique de mot de passe, verrouillage anti force brute, expiration, sessions ;
  • la Vérification renforcée (MFA) — code OTP à usage unique envoyé par e-mail (SMTP), affiché en mode démonstration ;
  • l'Accès (SSO) — Single Sign-On par jeton à usage unique : une connexion IAM donne accès aux applications enregistrées (accès fluide via le portail, ressaisie facultative sur lien direct) ;
  • la Gouvernance (RBAC) — rôles, permissions, affectations utilisateur/rôle/application, journal d'audit complet ;
  • l'Administration graphique — une console de gestion ne nécessitant aucune manipulation SQL en exploitation.

Périmètre. Le présent document décrit l'existant implémenté (version 1.0.0), qui sert de socle au déploiement et aux évolutions ultérieures.

2. Périmètre fonctionnel

2.1 Authentification

  • Connexion par identifiant (e-mail) et mot de passe haché (bcrypt via password_hash).
  • Comptes avec statuts active / inactive / locked / pending, premier mot de passe imposé (must_change_password = 1), expiration de mot de passe configurable.
  • Anti force brute : 5 échecs autorisés → verrouillage 30 min (tentatives journalisées dans login_attempts).
  • Double vérification MFA par e-mail : OTP de 6 chiffres, valable 5 minutes, 5 essais max (MFA_FORCE_ALL = true, sauf administrateurs).
  • Connexion sans mot de passe : e-mail ou téléphone + code OTP à usage unique envoyé par e-mail (otp_login.php, canal d'envoi email), verrouillage renforcé, reprise en ?resend=1.
  • Session PHP dédiée iam_session (durée 3600 s, inactivité 1800 s), sessions révocables depuis l'administration.

2.2 SSO applicatif

  • Entrepôt sso/authorize.php?app=CODE&return=URL[&prompt=login] : vérifie l'application, la session IAM, le MFA, l'expiration du mot de passe et l'accès de l'utilisateur, puis émet un jeton à usage unique (60 s, enregistré dans sso_tokens).
  • Fichier garde généré iam-sso-<code>.php (déployé automatiquement via l'administrateur ou téléchargeable ; chargé en auto_prepend_file via .htaccess) : session isolée côté application, validation du jeton via api/sso/validate.php, reconstruction de l'utilisateur (rôles, permissions).
  • Paramètre par application sso_prompt (administré graphiquement) : ajoute prompt=login sur accès direct ⇒ ressaisie des identifiants IAM ; via le portail l'accès reste fluide.
  • Vérification de la légitimité de l'URL de retour (même hôte que l'application) avant émission du jeton.

2.3 Portail & applications

  • Portail (page d'accueil) : grille d'applications autorisées avec icône, couleur et description ; accès en un clic (lien SSO).
  • Catalogage des applications : code, nom, URL, redirect_uri, client_id/client_secret, active, sso_prompt, is_system.

2.4 Gouvernance (RBAC) et administration graphique

  • Rôles & permissions : création/édition/suppression de rôles (rôles système protégés), attribution de permissions par application.
  • Utilisateurs : création, modification (statut, organisation, direction / service / fonction), réinitialisation de mot de passe, suppression, import CSV (modèle téléchargeable, doublons ignorés, mots de passe aléatoires, rapprochement des directions insensible aux accents).
  • Groupes : annuaires nommés (création, renommage, suppression, affectation des membres) ; multi-sélection dans les formulaires utilisateur.
  • Organisations : arborescence Ministère/Direction/Service/Bureau avec affectation des utilisateurs.
  • Sessions : consultation, filtrage par utilisateur, révocation individuelle ou totale.
  • Journal d'audit : recherche textuelle et filtrage par action sur audit_logs.
  • Paramètres : politique de mots de passe, durée de session et d'inactivité, paramètres API & sécurité (origines CORS autorisées, géolocalisation optionnelle des IP, anti force brute par IP).
  • E-mail & MFA : configuration SMTP (Gmail/Outlook, clé applicative), envoi de test, guide pas à pas à 3 étapes.
  • Applications : création, édition, permissions, accès utilisateurs, déploiement/retrait du garde SSO, téléchargement du garde.
  • OAuth / OIDC : console de gestion des clients (identifiants, secret affiché une seule fois, URI de redirection, grants autorisés, scopes) et rotation de la clé de signature RSA (JWKS).

2.5 API et intégration

  • API JSON : api/login.php, api/sso/validate.php, api/sso/app_config.php, api/userinfo.php, gestion des utilisateurs/rôles/permissions/applications/sessions, audit, réinitialisation de mot de passe, MFA (envoi/vérification).
  • Bibliothèque client client/iam_client.php (helper iam_client_requires_prompt(), etc.) et client/sso_handler.php.
  • Serveur d'autorisation OAuth 2.0 / OIDC (free flow Authorization Code + PKCE) : oauth.php (point d'autorisation + consentement), api/oauth/token.php (authorization_code, client_credentials, refresh_token avec rotation), api/oauth/userinfo.php, api/oauth/jwks.php, découverte .well-known/openid-configuration.php (racine et API). Émission d'id_token signé RS256, refus journalisé (access_denied), PKCE par défaut.

4. Diagrammes d'activité

Deux diagrammes d'activité (UML) décrivent les flux critiques : 4.1 le flux SSO de bout en bout (portail → application → IAM) et 4.2 la phase d'authentification avec MFA par e-mail et changement de mot de passe. Les pointillés représentent le retour d'une branche forcée (re-contrôle dans authorize.php).

4.1 Flux SSO de bout en bout

L'utilisateur accède à une application protégée par le garde iam-sso-<code>.php (chargé via auto_prepend_file). Si la session locale de l'application est absente, sso/authorize.php contrôle la session IAM, le MFA, le mot de passe et l'accès RBAC, puis émet un jeton à usage unique validé par api/sso/validate.php.

Le chemin en pointillés ramène l'utilisateur vers authorize.php après une action forcée (login, MFA, changement de mot de passe) : les contrôles sont renouvelés, puis un jeton sso_tokens est émis et validé par la garde auprès de api/sso/validate.php (la branche « oui » de D1 devient active pour les accès suivants).

4.2 Authentification, MFA par e-mail et changement de mot de passe

Flux interne de login.php puis mfa.php : anti force brute (5 échecs → verrouillage 30 min), code OTP à 6 chiffres (5 minutes, 5 essais, envoi SMTP), puis bascule obligatoire vers profile.php?force=1 si must_change_password ou expiration atteinte.

Les boucles en pointillés relancent la saisie ; le « non » après la validation du mot de passe revient à l'écran de connexion. Un nouvel échec incrémente login_attempts ; dès le seuil de 5, le compte est verrouillé 30 minutes (locked_until). Une fois MFA vérifié et mot de passe à jour, l'accès est transmis au portail ou, via le +SSO, au retour de authorize.php.

5.2 Mesures de sécurité

  • Anti force brute positionnable (verrouillage après 5 échecs / 30 min), journalisé.
  • Anti force brute par adresse IP sur les pages et API de connexion : 60 échecs / 15 min (paramétrable en constantes).
  • Origines CORS d'accès à l'API paramétrables (settings.cors_origins, défaut *).
  • Géolocalisation optionnelle des adresses IP publiques dans l'audit (service ip-api.com, sans stockage ; IP locales = « Réseau local »).
  • Protection CSRF sur toutes les actions d'administration (jeton de session).
  • Échappement HTML systématique (htmlspecialchars) sur les saisies restituées.
  • Vérification de l'hôte dans l'URL de retour SSO (anti redirection ouverte).
  • CURL côté application : vérification SSL activée (CURLOPT_SSL_VERIFYPEER).
  • Journal d'audit horodaté : connexions, MFA, SSO, admin (création, suppression, droits…).
  • Rôles système non supprimables, applications système non supprimables.
  • OAuth 2.0 : validation stricte de la redirection (anti redirection ouverte), PKCE S256 (ou plain) comparé via hash_equals, codes d'autorisation à usage unique, rotation des refresh tokens (l'ancien est révoqué), scopes sur liste blanche, clé signée RS256 + rotation.
