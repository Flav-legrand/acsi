01 · Vue d’ensemble

À quoi sert IAM-Local ?

IAM-Local est une plateforme d’Identity and Access Management (IAM) écrite principalement en PHP. Elle fournit un point central pour authentifier les personnes, publier les applications disponibles et définir les droits par application.

Ce que l’IAM centralise

  • Comptes, profils, états et rattachements organisationnels.
  • Connexion, politique de mot de passe, MFA et sessions.
  • Catalogue d’applications, rôles, permissions et attributions.
  • Journal d’audit et émission de jetons SSO/OIDC.

Ce que l’IAM ne remplace pas

  • Le code métier, les écrans et les données de chaque application.
  • La base de données métier de l’application cliente.
  • Le contrôle de permission dans une application qui n’applique pas les droits reçus.

Architecture simplifiée

UtilisateurOuvre le portail ou une application.
→
IAM-LocalAuthentifie, vérifie MFA et autorisations.
→
Application clienteÉtablit sa session et contrôle les permissions.
Deux mécanismes d’intégration. Le SSO natif émet un jeton court à usage unique échangé côté serveur. OAuth 2.0 / OIDC suit un protocole standard et convient aux clients Django, Flutter ou autres frameworks qui disposent d’un connecteur OIDC.

Environnement documenté : PHP 8.x, Apache/WAMP, MySQL et URL locale http://localhost/IAM-Local. Ce guide décrit le dépôt IAM-Local; les projets métier voisins restent des applications séparées.

03 · Modèle métier

Identités, applications et droits

Le contrôle d’accès suit le modèle RBAC : un utilisateur reçoit un ou plusieurs rôles pour une application; chaque rôle regroupe des permissions.

Ensemble de tablesContenuPourquoi c’est important
users, organizations, groups, user_groupsIdentités et structure organisationnelle.La connexion identifie l’utilisateur; le statut détermine s’il peut continuer.
applicationsCode, nom, URL, état, configuration de pont SSO.Le portail affiche les applications actives; l’autorisation vérifie la cible.

Conséquence pratique. Si la liste de rôles est vide pour une nouvelle application, ce n’est pas nécessairement une panne : il faut créer un rôle propriétaire de cette application, lui attacher des permissions, puis attribuer ce rôle à l’utilisateur.

Le schéma de référence est sql/schema.sql; certains déploiements anciens sont adaptés par des migrations idempotentes au démarrage ou à la mise à niveau.

04 · Parcours d’authentification

Comment une connexion se déroule

Connexion au portail IAM

  1. L’utilisateur saisit identifiant/e-mail/téléphone et mot de passe.
  2. IAM contrôle le statut, le hash bcrypt, les tentatives et le verrouillage.
  3. Selon la politique, IAM exige le MFA par code e-mail.
  4. Un changement de mot de passe peut être imposé au premier accès ou après expiration.
  5. IAM ouvre sa session puis affiche le portail et les applications autorisées.

SSO natif vers une application cliente

1 · DemandeLe garde intercepte l’accès et redirige vers IAM.
→
2 · ContrôlesIAM vérifie application active, session/MFA et rôle.
→
3 · JetonJeton aléatoire, expiration courte (60 s par défaut), usage unique.
→
4 · ÉchangeL’application appelle api/sso/validate.php et ouvre sa session locale.

L’application reçoit profil, rôles et permissions filtrés pour son identifiant. Elle doit ensuite vérifier les permissions sur ses pages et actions; l’IAM ne peut pas deviner les opérations métier propres à l’application.

OIDC Authorization Code + PKCE

OIDC convient aux frameworks non-PHP qui ont un connecteur : redirection vers l’autorisation IAM, consentement, retour avec un code, échange contre des jetons, puis lecture du profil via UserInfo. Django utilise un client confidentiel côté serveur; Flutter utilise un client public sans secret avec PKCE S256.

Intégration selon la technologie

PHP local

Garde généré, auto-prepend Apache si le module et les droits le permettent; sinon inclusion manuelle. Le garde appelle l’API de validation.

Django / serveur

Client OIDC confidentiel. Le secret reste côté serveur; callback HTTPS exact en production. Utiliser une bibliothèque OIDC maintenue.

Flutter / mobile

Client public sans secret. PKCE S256 obligatoire; URI de callback native déclarée à l’identique dans l’app et IAM.

SPA / autre framework

Doit disposer d’un connecteur OIDC. Les secrets ne vont jamais dans le navigateur. Une passerelle ou un adaptateur peut être nécessaire.

L’enregistrement graphique prépare les paramètres du client; il ne peut pas installer automatiquement une bibliothèque ou modifier un projet externe arbitraire.

08 · Installation et exploitation

Installer, configurer, vérifier

Prérequis locaux

  • Apache avec PHP 8.x et extensions PDO MySQL, OpenSSL et mbstring.
  • MySQL; la base par défaut est iam_local.
  • Composer pour PHPMailer et les dépendances OAuth.
  • WAMP/XAMPP ou environnement équivalent; démarrer Apache et MySQL avant l’installation.

Séquence d’installation

  1. Placer le dépôt dans le document root web sous IAM-Local.
  2. Ouvrir /IAM-Local/install.php.
  3. Renseigner l’URL de base, la connexion MySQL et le compte administrateur initial.
  4. Choisir si les données de démonstration doivent être chargées.
  5. Enregistrer le mot de passe initial de façon sûre, changer-le à la première connexion, puis contrôler les comptes et rôles.
  6. Installer les dépendances Composer avec composer install si elles ne sont pas déjà présentes.

Points de contrôle après installation

Connexion
Le login accepte les identifiants prévus; MFA et SMTP réagissent selon la configuration.
Portail
L’application apparaît uniquement si elle est active et l’utilisateur autorisé.
SSO PHP
L’état d’intégration indique garde déployé, manuel ou erreur de chemin/droits.
OIDC
Découverte JSON, callbacks, PKCE, UserInfo et JWKS sont atteignables.
Ne pas relancer une réinstallation sans sauvegarde. L’installateur est conçu pour initialiser/mettre à niveau; vérifier son comportement et sauvegarder la base avant toute opération de maintenance sur des données utiles.

Dépannage rapide

SymptômeVérifications
Application absente du portailActive; utilisateur lié à un rôle de cette application; rôle avec permissions attendues.
Jeton SSO invalideRecommencer depuis le portail; jeton expiré ou déjà consommé; vérifier l’app_code et l’application cible.
Garde PHP non actifÉtat de déploiement, chemin local, écriture du fichier, module PHP Apache et `.htaccess`.
OIDC redirect_uri invalideURI callback exactement identique à celle enregistrée, y compris schéma, port et slash final.
Flutter n’échange pas le codeClient public, aucune authentification par secret, PKCE S256, verifier/challenge issus de la même transaction.

09 · Limites et plan de compréhension

Ce qu’il faut retenir

Forces du projet

  • Parcours identités, MFA et SSO déjà réunis.
  • Console pour utilisateurs, applications, rôles, permissions et audit.
  • Modèle RBAC par application inspiré des clients/roles.
  • SSO natif simple pour les applications PHP locales.
  • OIDC utilisable par des clients confidentiels et publics PKCE.

Limites à garder visibles

  • Le garde auto-déployé n’est pas universel : il protège les applications PHP compatibles.
  • Un framework externe doit avoir un connecteur OIDC ou un adaptateur préinstallé.
  • UserInfo OIDC ne fournit pas actuellement les rôles applicatifs.
  • Les données métier des applications clientes restent dans leurs propres bases.
  • L’environnement local de démonstration n’est pas un profil production.

Ordre de lecture conseillé du code

  1. install.php et sql/schema.sql : initialisation et modèle de données.
  2. includes/functions.php : sessions, utilisateurs, RBAC, OTP, tokens et audit.
  3. login.php, mfa.php et portal.php : parcours utilisateur.
  4. sso/authorize.php, api/sso/validate.php et admin/_sso_generator.php : SSO natif.
  5. includes/oauth.php, oauth.php et api/oauth/ : OIDC.
  6. admin/ : workflows graphiques et contrôles des données.

Glossaire

IAM : gestion des identités et accès. SSO : connexion unique entre applications. OIDC : protocole d’identité basé sur OAuth 2.0. RBAC : droits attribués par rôle. PKCE : preuve cryptographique qui protège l’échange du code pour les clients publics. JWKS : publication des clés publiques nécessaires à la vérification des jetons signés.

Document de compréhension du dépôt IAM-Local · Source technique : code PHP, schéma SQL et documentation présents dans le projet · Aucune valeur de secret incluse.

10 · Manuel d’utilisation

Première connexion et navigation

Cette partie explique les actions courantes dans l’interface, sans avoir besoin de lire le code.

Ouvrir une session

  1. Ouvrir http://localhost/IAM-Local/login.php.
  2. Saisir l’identifiant ou l’adresse e-mail et le mot de passe transmis par l’administrateur.
  3. Dans la configuration actuelle, le MFA est demandé aux comptes non administrateurs. Saisir le code reçu par e-mail; sans SMTP configuré, le mode de démonstration affiche le code à l’écran.
  4. Si un changement de mot de passe est demandé, le faire avant de continuer.
  5. Le portail affiche les applications actives auxquelles le compte a reçu un rôle.

Portail utilisateur

Ouvrir une application, consulter le profil, changer le mot de passe et voir ses sessions selon les options disponibles.

Console d’administration

Accessible depuis /admin/ aux administrateurs IAM. Un rôle « admin » métier dans une autre application ne donne pas ces droits.

Déconnexion et sessions

La déconnexion ferme la session IAM courante. Un administrateur peut révoquer une session depuis Administration → Sessions; l’utilisateur peut fermer ses autres sessions depuis son profil. Valeurs par défaut : durée maximale d’une heure et déconnexion après 30 minutes d’inactivité.

Incident de sécurité. Désactiver le compte puis révoquer ses sessions; retirer uniquement son accès à une application ne coupe pas une session déjà ouverte.

11 · Comptes et organisation

Créer et administrer les utilisateurs

Créer un compte

  1. Ouvrir Administration → Utilisateurs → Nouvel utilisateur.
  2. Renseigner prénom, nom, e-mail et mot de passe; compléter téléphone, identifiant, matricule et informations de poste si connus.
  3. Choisir l’organisation si elle est déjà créée. Les rôles sont attribuables depuis cette fiche ou depuis la carte de l’application.
  4. Enregistrer et transmettre les informations d’accès par un canal sûr.

Modifier, réinitialiser ou désactiver

  • Rechercher la personne par nom, e-mail ou matricule; utiliser Modifier pour le profil, l’organisation, les groupes, le statut et les rôles.
  • Utiliser Réinitialiser le mot de passe en cas d’oubli, puis communiquer le nouveau mot de passe de façon sécurisée.
  • Désactiver un compte pour interdire les prochaines connexions; révoquer aussi les sessions ouvertes si nécessaire.
  • La suppression est définitive; le compte administrateur principal est protégé.

Importer plusieurs personnes par CSV

  1. Dans Utilisateurs, télécharger le modèle CSV fourni par l’interface.
  2. Conserver les en-têtes. Les colonnes obligatoires sont email, first_name et last_name; les autres couvrent identifiant, téléphone, matricule, organisation, direction, service, fonction et statut.
  3. Remplir en UTF-8; virgule ou point-virgule est accepté. Les e-mails déjà existants sont ignorés.
  4. Importer et lire le bilan des comptes créés, doublons et lignes rejetées; distribuer les accès temporairement par un canal sûr.
Créer d’abord les organisations, puis les utilisateurs : le rattachement hiérarchique sera disponible dans leurs formulaires.

12 · Ajouter une application

Suivre l’assistant d’intégration

Ouvrir Administration → Applications → Ajouter une application. L’assistant en trois étapes enregistre le projet au catalogue et vérifie le type d’installation.

Étape 1 — Informations de l’application

  1. Saisir le nom affiché aux utilisateurs.
  2. Vérifier le code technique proposé; il doit être unique et utilise lettres minuscules, chiffres et tirets.
  3. Saisir l’URL que les utilisateurs ouvriront, puis une description facultative.
  4. Cliquer sur Continuer.

Étape 2 — Connexion IAM

  1. Le SSO natif est le parcours prévu pour un garde PHP. Pour Django ou Flutter, ouvrir OAuth / OIDC.
  2. Cocher « Redemander le mot de passe IAM » uniquement si la politique le demande à chaque accès direct.
  3. Cliquer sur Vérifier la configuration. Lire chaque contrôle : code disponible, URL, dossier local, droits d’écriture, serveur PHP.
  4. Un projet distant ou non inscriptible peut continuer en installation manuelle; son fichier de garde sera téléchargeable après création.

Étape 3 — Vérification et création

  1. Vérifier nom, code, URL et mode d’installation.
  2. Laisser désactivé tant que rôles et accès ne sont pas prêts; cocher « Activer dès sa création » seulement si la configuration est déjà préparée.
  3. Cliquer sur Créer et installer. Le serveur répète les validations avant l’enregistrement.
  4. Créer les permissions puis les rôles, attribuer un rôle à un utilisateur, activer et utiliser Tester le parcours SSO.
Une application n’a pas automatiquement de rôles. La liste des rôles vide est normale à la création : les rôles sont propres à chaque application et se configurent séparément.

13 · Permissions et accès

Définir qui peut faire quoi

PermissionsActions métier reconnues par l’application.
→
RôlesProfils qui regroupent les permissions.
→
UtilisateursPersonnes autorisées dans l’application.

Créer les permissions

Dans la carte d’application, ouvrir Permissions puis ajouter nom, code et description. Exemples : mnt.equipement.view, mnt.intervention.assign ou mnt.piece.manage. Les codes doivent être contrôlés par le backend métier pour réellement protéger les actions.

Créer un rôle et lui affecter des droits

  1. Ouvrir Rôles & permissions → Créer un rôle.
  2. Définir son nom, son code, sa description et choisir l’application propriétaire.
  3. Sur la carte du rôle, ouvrir Permissions, cocher les droits nécessaires et enregistrer.

Attribuer le rôle à une personne

  1. Dans la carte de l’application, ouvrir Accès utilisateurs.
  2. Choisir un utilisateur actif et un rôle de cette application.
  3. Cliquer sur Donner l’accès. Pour retirer l’accès, utiliser l’action de retrait dans la liste.
Rôle typeExemple de périmètre
Lecteur / auditeurConsultation; export seulement s’il est explicitement accordé.
Agent / opérateurConsultation et saisie limitée à son activité.
GestionnaireCréation, modification, affectation et validation selon le métier.
Admin applicatifAdministration de son application; ne donne pas l’administration de la plateforme IAM.
Moindre privilège. Ne pas donner un rôle d’administration pour résoudre un manque de permission ponctuel. Ajouter plutôt la permission exacte au rôle métier concerné.

14 · Opérations quotidiennes

Groupes, organisations, sessions et audit

Organisations

  1. Créer les niveaux racines.
  2. Ajouter directions, services et bureaux en choisissant leur parent.
  3. Rattacher les utilisateurs depuis leur fiche.

Une organisation utilisée doit être vidée ou ses utilisateurs déplacés avant suppression.

Groupes

  1. Ouvrir Groupes → Nouveau groupe.
  2. Nommer et décrire le groupe.
  3. Ouvrir Modifier pour choisir ses membres; les groupes peuvent aussi être cochés dans la fiche utilisateur.

Un groupe organise les personnes; il ne remplace pas un rôle applicatif.

Sessions

Filtrer par utilisateur, lire IP/navigateur/activité, puis révoquer une session précise ou toutes les sessions d’un compte.

Audit

Rechercher par compte, action ou IP. Contrôler les connexions, changements de droits, opérations SSO/OIDC et révocations.

Paramètres et MFA

Administration → Paramètres permet d’ajuster complexité, historique, expiration du mot de passe, verrouillage et durées de session. E-mail & MFA contient les paramètres de livraison des codes. Sans SMTP fonctionnel, les codes sont visibles en mode de démonstration; ne pas utiliser ce mode en production.

Point à connaître. L’état MFA et la règle qui l’impose dépendent de la configuration; la MFA n’est pas un rôle. Un utilisateur peut être autorisé par rôle et néanmoins devoir passer le second facteur avant d’entrer.

15 · OAuth / OIDC

Configurer une application non-PHP

Ouvrir Administration → OAuth / OIDC → Nouveau client et choisir une plateforme. L’assistant enregistre le client et affiche un récapitulatif de paramètres; il ne modifie pas le code d’un projet externe.

ChoixConfigurationRègle de sécurité
Django / serveur webCallback HTTPS exacte; Authorization Code; scopes openid/profile/email.Secret visible une seule fois, à garder côté serveur.
Flutter mobileCallback avec schéma de l’application; client public Authorization Code.Pas de secret; PKCE S256 est obligatoire.
Service APIClient Credentials; pas de callback ni d’utilisateur interactif.Secret côté serveur et scopes machine autorisés.

Paramètres à renseigner dans le connecteur OIDC

  • Issuer : URL IAM indiquée dans le récapitulatif.
  • Découverte : /.well-known/openid-configuration.php.
  • Client ID; secret uniquement pour serveur/service confidentiel.
  • URI callback exactement identique; scopes autorisés affichés.
  • Pour Flutter : redirect scheme exact et PKCE S256; jamais incorporer un secret à l’application.
Test fonctionnel. Lancer le login depuis l’application, approuver le consentement, confirmer le retour à l’URI, vérifier le profil UserInfo puis tester déconnexion et session expirée.
Les rôles RBAC ne sont pas encore des claims UserInfo. OIDC renvoie l’identité/profil. Les permissions applicatives doivent être ajoutées à une future extension de claims ou vérifiées via un endpoint adapté.

16 · Aide-mémoire

Scénario complet et dépannage

Ouvrir une application de bout en bout

  1. Créer l’application au catalogue et lancer le prédiagnostic.
  2. Ajouter ses permissions correspondant aux opérations métier réelles.
  3. Créer des rôles propres à l’application et attacher les permissions.
  4. Créer les utilisateurs ou les importer; créer l’organisation au préalable si nécessaire.
  5. Attribuer un rôle à chaque utilisateur dans la bonne application.
  6. Configurer le garde PHP ou enregistrer un client OIDC adapté.
